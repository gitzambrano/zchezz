# Training Datasets and Provenance Catalog

This document defines the dataset conventions, schema rules, and the complete catalog of training datasets for Zchezz.

## 1. Nomenclature and Conventions

Zchezz uses a closed vocabulary for evaluation and target values. Every score is White-relative.

| Term | Meaning | Range | Persistence |
|---|---|---|---|
| `cp` | Position evaluation in centipawns | Integer, White-relative | Stored in dataset column `cp` |
| `result` | Actual game outcome | `0.0` (Black won), `0.5` (Draw), `1.0` (White won) | Stored in dataset column `result` |
| `wdl` | `sigmoid(cp / 320)` win/draw/loss probability | Float in `0.0..1.0`, White-relative | Computed at training time; never stored |
| `target` | Blended training target: `lambda * result + (1 - lambda) * wdl` | Float in `0.0..1.0`, White-relative | Computed dynamically by trainer |

### Governing Rules

1. `wdl` is never stored as a column. It is an exact mathematical function of `cp`. Storing both permits values to diverge.
2. `lambda` blending requires both `cp` and `result`. If a dataset contains only `cp`, `lambda` is inert.
3. `result` uses only `0.0`, `0.5`, or `1.0`. Blanks remain missing; they are not imputed as draws.
4. Scale constant `320` matches `CP_TO_WDL_T` in training and `_nnL3B * 320.0f` in C runtime evaluation.
5. Engine scores reach `cp` through `utils/uci_score.py`. Zchezz engines (all profiles) print `score cp` White-relative. `v335`, `v510` and `v605` print `score mate N` White-relative (N > 0 when White mates); older builds print it without a usable sign. For every Zchezz build the parser takes the mate sign from the last `cp` of the same line. Standard UCI engines such as Stockfish print scores relative to the side to move. The runners detect the convention from `id name`; override it with `--score-pov white|stm`. `tests/test_uci_score_pov.py` checks known positions for each built engine.
6. Run `python train/labeling/audit_datasets.py` before you train on new or changed data. It reads every file of every dataset; `--dataset NAME` limits it to one. `--data-root DIR` audits the dataset directories under another directory, for example `/content/drive/MyDrive/zchezz_data` in Colab. It checks FEN syntax, the `cp` and `result` ranges, and the sign of `cp` for each side to move, against both the material balance and `result`. A dataset whose `cp` is relative to the side to move fails with Black to move. The report goes to `artifacts/data_audit/<UTC>/report.json`, and the exit code is 1 when a file fails. Chess960 FENs (Shredder castling letters) and EPD FENs without move counters are valid. A row without `cp` but with a `result` is a warning, because the trainers use the result alone for it.
7. The generators that write `.bin` shards (`engine/build/selfplay.exe`, `engine/build/arena.exe`, `tests/run_selfplay.py --bin`, `tests/run_tournament_quick.py --bin`) store `eval_cp` and `game_result` relative to the side to move. Before the Colab self-play job (`colab/remote/run_selfplay_colab.sh`) persists a shard, it refuses the shard if `eval_cp` contradicts `game_result` for either side to move. Before the Colab trainer (`colab/remote/run_train_colab.sh`) trains, it audits the Drive folders it reads and stops when a file fails.
8. The dense lookahead target (`.bin` sources with `k < 1`) reads the later plies of the same game by global row index (`train/dataset.py: dense_lookahead_target_indexed`). It stops at a game or shard boundary: the next row must be in the same shard, the side to move and `game_result` must alternate, and the piece count must not grow. After the boundary it uses the game result. Trainers sample random rows, so they must not apply the single-game `dense_lookahead_target` to a sampled batch. `tests/test_lookahead_target.py` checks this. Models trained on `.bin` shards with `k < 1` before this rule (for example `colab/remote/run_train_colab.sh` with its default `K=0.1`) used targets that mixed rows of different games.

### Dataset Directory Naming Standard

Directory names append tags in this canonical order:
`<source>_<core>_<cp>_<evaluator>_<res>_<endgames>_<filter>_<data>`

| Tag | Meaning |
|---|---|
| `_cp` | Contains an evaluation column (`cp`) |
| `_res` | Contains a game result column (`result`) |
| `_filter` | Filtered for quiet (non-tactical) positions |
| `_raw` | Unfiltered, raw source data |
| `_endgames` | Endgame positions only |
| `_data<YYYYMMDD>` | Generation date with four-digit year |
| `_sf<budget>` | Evaluated by Stockfish with node budget (e.g. `sf50k`, `sf100k`) |
| `_sfd<depth>` | Evaluated by Stockfish with depth budget (e.g. `sfd12`, `sfd14`) |
| `_sfdb` | Stockfish evaluations bundled directly with upstream database |
| `_zchezz` | Evaluated by Zchezz search during self-play |
| `selfplay_` | Generated by self-play games of Zchezz |
| `synthetic_endgame_` | Procedurally generated positions without played games |

## 2. Dataset Manifests (`manifest.json`)

Every dataset directory `data/<name>/` carries `manifest.json` (schema version 2).
The data files are ignored by git; the manifests are tracked, so the provenance
record survives if the data is lost. `train/labeling/manifest.py` owns the format.

- **Measured fields** (`format`, `files_count`, `positions_count`, `size_bytes`,
  `columns`, `has_cp`, `has_result`, `result_rate`, `result_distribution`) are
  recomputed from the files on every refresh. Result statistics cover every row.
  `result_distribution` counts White wins, draws and Black wins.
- **Provenance fields** (`source`, `played_by`, `engine_version`, `engine_commit`,
  `evaluator`, `eval_budget`, `date`, `filter_type`, `raw_source_input`) and the
  usage field `stage` each carry an evidence level in `evidence[field]`.
- `producer` holds the producing tool's configuration when the tool wrote it.
  `notes` is free text for the owner.

| Evidence | Meaning |
|---|---|
| `recorded` [R] | Written by the producing tool when the data was generated |
| `owner` [O] | Stated by the project owner |
| `measured` [M] | Computed from the files |
| `inferred` [I] | Parsed from the directory name; a guess, not a fact |
| `unknown` [?] | No information |

A refresh never replaces a value with one of weaker evidence. `recorded` and
`owner` values therefore survive `--generate`; correct a wrong value by editing
the manifest and setting its evidence to `owner`.

Producers:

- `train/labeling/process_positions.py` writes the manifest of its output
  directory. It records the input, the commit, the filters and, when Stockfish
  relabels `cp`, the evaluator and node budget. When `cp` passes through, it
  copies evaluator and origin from the input directory's manifest.
- `tests/run_selfplay.py` writes the manifest of `RESULTS_DIR` with the engines,
  time control, seed and opening settings. The manifest covers every file in that
  directory, so use one directory per run.

Commands:

```bash
python train/labeling/manifest.py              # read-only status
python train/labeling/manifest.py --generate   # refresh every manifest
python train/labeling/manifest.py --catalog    # re-render the table below
```

`stage` names the mix in `train_nnue.py`'s `STAGE` switch: `warmup` (random
weights, crude and large human data), `finetune` (recent strong sets),
`excluded` (judged low quality). Datasets whose cp came from Zchezz's own search
teach the network its current opinion; at lambda=0 only their `result` adds an
independent signal. `lambda` is inert unless a dataset has both `cp` and `result`.

### Quarantine

`data/_quarantine/` holds files that the trainers and the catalog must not read. Each file stays there with the reason in its directory name:

| Directory | Content | Reason |
|---|---|---|
| `selfplay_v331_filter.original_stm_cp/` | The `selfplay_v331_filter` files before the correction | `cp` was relative to the side to move on rows with Black to move |
| `selfplay_lookahead_filter.v331_inverted_cp/` | Shards `chunk_00000`–`00011` of `selfplay_lookahead_filter` (1,136,597 rows) | Targets come from the inverted v331 `cp` and the result. A sign flip cannot repair them |
